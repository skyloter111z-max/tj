# v5 기획서 — 구독관리 앱 (오픈뱅킹 연동 / 연 1,200원 / 1인 운영)

> **작성일:** 2026-10-03
> **범위:** 일반 소비자용 구독 지출 관리 앱. **연동은 오픈뱅킹, 가격은 연 1,200원, 운영은 1인.** N빵 매칭·B2B는 이 문서에 없다.
> **승계 없음:** v2.1~v4는 보류. 이 문서는 처음부터 다시 쓴 것이다.

---

## 0. 연동 방식 — 흔한 오해부터 정정

**카드사 앱에서 끌어오는 방식이 아니다.** 그것은 스크래핑이고 **2022년 1월 5일부터 금지**됐다. 오픈뱅킹은 **서버 대 서버**다.

```
[사용자]  구독모아 앱 → "내 카드·계좌 연결" 1회 탭
             │
             ▼
   오픈뱅킹 인증 페이지 (금융결제원)
   · 휴대폰 본인인증
   · ARS 동의
             │
             ▼
   Access Token + 핀테크이용번호(fintech_use_num) 발급
             │
             ▼
[구독모아 서버] ──── API 호출 ────▶ [금융결제원] ──▶ [카드사·은행]
   (사용자 개입 없음, 월 1회 배치)
```

| 오해 | 사실 |
|---|---|
| 카드사 앱이 로그인돼 있어야 한다 | **무관.** 설치돼 있지 않아도 된다 |
| 폰에서 알림·화면을 읽는다 | **아니다.** 서버가 금융결제원 API를 호출한다 |
| 사용자가 매번 뭘 해야 한다 | **1회 본인인증·동의 후 끝.** 이후 전자동 |

**사용자 작업은 최초 1회, 1~2분이다.** 그 뒤로는 사용자가 아무것도 하지 않는다.

**진입 자격:** 금융결제원 **이용계약 + 이용승인**을 받은 핀테크사업자. **마이데이터 허가(자본금 5억 + 금융위 허가)가 아니다.** 보안심사가 있다.

## 1. ✅ 전제 확인 완료 (2026-10-03) — 통과, 단 조건이 붙는다

`카드청구상세정보조회` 명세를 확인했다. **개별 거래 건이 온다 — 사업 전제는 통과했다.**
단 두 가지 조건이 붙고, 둘 다 설계를 바꾼다.

### 1.1 확인된 응답 명세

| 필드 | 형식 | 내용 |
|---|---|---|
| `bill_list` | object | 청구상세목록 — **한 페이지 최대 20건** |
| `card_value` | aN(64) | 카드 식별값 |
| `paid_date` | N(8) | **사용일자 (YYYYMMDD)** ✅ |
| `paid_time` | N(6) | 사용시간 (hhmmss) |
| `paid_amt` | SN(13) | **이용금액 (원)** ✅ (음수 가능) |
| **`merchant_name_masked`** | **AH(40)** | **🔴 마스킹된 가맹점명** (예시 `"오픈**"`) |
| `credit_fee_amt` | SN(13) | 신용판매 수수료 |
| `product_type` | aN(2) | 상품 구분 |
| `next_page_yn` / `befor_inquiry_trace_info` / `bill_detail_cnt` | | 페이지네이션 |

비교 — `카드청구기본정보조회`는 월별 총액만 준다 (`charge_month`, `charge_amt`, `settlement_day`, `settlement_date`, `card_id`).

### 1.2 🔴 조건 1 — 가맹점명이 마스킹된다

필드명이 `merchant_name_masked`이고 예시가 `"오픈**"`이다. **앞 몇 글자만 남는다.**

따라서 가맹점명 패턴 매칭이 듣지 않는다. 식별 신호의 우선순위가 뒤집힌다.

| | 마스킹 전 가정 (v5 초안) | **실제** |
|---|---|---|
| 1차 신호 | 가맹점명 패턴 | **금액 (구독료는 상수)** |
| 2차 신호 | — | 드러난 접두 2글자 |
| 확정 조건 | 패턴 일치 | **접두 + 금액이 함께 일치** |

**금액이 접두보다 판별력이 높다.** 넷플릭스 스탠다드는 정확히 13,500원이고 ChatGPT Plus는 29,000원이다.
접두와 금액이 함께 맞을 때만 확정하고, 하나만 맞거나 후보가 여럿이면 미분류로 남긴다 —
**틀린 이름을 보여주는 것이 모르는 것보다 나쁘다.**

남는 한계:
- 해외 결제는 환율로 금액이 흔들린다 → ±5% 허용으로 흡수
- 접두와 가격이 모두 겹치는 쌍은 구분 불가 (Claude Pro·Perplexity Pro 둘 다 27,000원)
- 결제대행사를 거치면 접두가 서비스가 아닌 PG 이름이 된다 (`PADDLE.NET* OPENAI` → `PA**`)

### 1.3 조건 2 — 호출이 2단계 체인이다

명세에 `settlement_seq_no`(결제순번)가 필수이고, 주석에 **"카드청구기본정보조회 응답 메시지 상의 청구년월 및 결제순번"**을 쓰라고 돼 있다. 즉 2단계 체인이고, 상세는 페이지당 20건이다.

```
카드목록조회              1회 (캐시 가능)
카드청구기본정보조회       1회  → charge_month + settlement_seq_no
카드청구상세정보조회       ceil(월 거래건수 / 20) 회
```

**1개월치 데이터를 받는 데 3회**다 (월 40건 기준: 기본 1 + 상세 2).

`charge_month`가 월 단위 파라미터이므로 **증분 조회가 된다** — 갱신할 때 전체 이력을 다시 받지 않고 새 달만 받는다. 호출 수는 **"몇 개월치를 받는가"**로 결정되며, 폴링 주기 자체가 아니다. 이것이 §3.1 조회 정책의 전제다.

### 1.4 그 외 확인된 제약

- **주2) 신용정보법에 의해 가족카드 이용내역은 미제공** — 가족카드 사용자는 커버되지 않는다
- **청구 기준이므로 지연이 있다.** 10/17 결제는 다음 청구월에 들어온다 → **신규 구독 알림이 최대 약 1개월 늦는다.** 무료체험 전환을 "결제 전에" 막지는 못하고, **두 번째 결제 전에** 알려주는 가치로 축소된다
- 카드 API의 건당 요율은 미확인이다. 위 계산은 계좌 거래내역조회(10원)를 준용했다 — **이용계약 시 확인 필요**

### 1.5 이용계약 전 확인 항목

요율과 과금 구조는 공개돼 있지 않다. 금융결제원(`openapi.kftc.or.kr` 문의 창구)에 **이용신청 전에** 물어야 할 것들이다. 답에 따라 §3의 마진이 바뀐다.

| # | 확인 항목 | 왜 중요한가 |
|---|---|---|
| **C1** | **카드 4개 API 각각의 건당 요율** (카드목록·카드기본정보·카드청구기본·카드청구상세) | 공개 요율은 계좌 API뿐이다(잔액 3원, 거래내역 10원, 실명 15원). 카드 API 요율은 미공개. §3.2는 10원을 준용한 값이다 |
| **C2** | **중소형사 경감비용 적용 기준** (월 이용금액·이용건수 임계값) | 차등은 카드사별이 아니라 **이용기관 규모별**이다. 1인 사업자는 경감 대상일 가능성이 높고, 2019년 기준 경감은 기본의 50~67%였다 |
| **C3** | **월 최소 이용료·기본료 존재 여부** | 🔴 **가장 큰 숨은 변수.** 최소 이용료가 있으면 사용자가 적을 때 건당 요율과 무관하게 고정비가 생기고 BEP가 크게 올라간다 |
| **C4** | **카드 API 호출 건수 산정 방식** | 페이지네이션 1페이지를 1건으로 세는가, 응답 레코드 수로 세는가. 후자면 비용이 20배가 된다 |
| **C5** | **조회 빈도·일일 한도 제한** | §3.1의 갱신 정책이 제한에 걸리는지 |
| **C6** | **보안심사 소요 기간·비용** | Phase 1 일정의 실제 길이 |
| **C7** | **카드사별 제공 범위 차이** | 명세상 제공 항목이라도 카드사가 실제로 채워 주는지는 다를 수 있다. 미참여·부분참여 카드사 목록 |

**C1·C3·C4가 사업 성립 여부를 가른다.** C4가 레코드 단위면 월 40건 조회에 40건 과금이 되어 연 1,200원이 즉시 깨진다.

## 2. 데이터 설계

### 2.1 카드 결제 구독 식별 (주 경로)

```
월 1회 배치
  ├ 카드목록조회            → 보유 카드 (최대 2장, §3.2)
  ├ 카드청구기본정보조회     → charge_month + settlement_seq_no
  └ 카드청구상세정보조회     → 건별 (paid_date, paid_amt, merchant_name_masked)
         │                      페이지당 20건, next_page_yn으로 순회
         ▼  정기결제 판정 엔진
  ┌────────────────────────────────────────────────────────┐
  │ 묶기   마스킹 가맹점명으로 그룹화                        │
  │        — 마스킹 규칙이 일정하므로 같은 가맹점은 같은 문자열 │
  │ 규칙 1  동일 그룹이 2회 이상 등장                        │
  │ 규칙 2  금액이 동일하거나 한 번만 계단식 변화(요금 인상)    │
  │ 규칙 3  결제 간격이 주/월/연 창에 들어감                  │
  │ 식별   접두 2글자 + 금액 지문이 함께 일치할 때만 확정       │
  └────────────────────────────────────────────────────────┘
         ▼
  구독 인벤토리 (서비스명·금액·주기·다음 결제일·신뢰도)
```

**마스킹이 묶기는 막지 않는다.** 마스킹 규칙이 일정하므로 `넷플**`은 매달 같은 문자열로 오고,
금액과 간격이 규칙적이면 그룹이 만들어진다. 마스킹이 막는 것은 **이름 붙이기**다.

그래서 식별은 **금액 지문**(`ServiceDef.prices`)과 **접두 후보**(`ServiceDef.maskedPrefixes`)
두 신호를 함께 쓴다(`lib/merchants.ts`의 `matchMaskedMerchant`). 둘 다 맞으면 확정,
하나만 맞으면 보류, 후보가 여럿이면 미분류다.

**미분류도 화면에는 올린다.** 이름 없이 "4,900원 · 매월 14일 · 확인 필요"로 보여주는 것이
숨기는 것보다 유용하고, 사용자가 그게 무엇인지 안다. 미분류 패턴은 수집해 사전을 키운다.

### 2.2 경로 B — 계좌 자동이체 (보조)

계좌 `거래내역조회` API는 **건별로 제공**된다 (명세 확인됨).

| 필드 | 내용 |
|---|---|
| `tran_date` / `tran_time` | 거래 일시 |
| `inout_type` | 입출금 구분 |
| **`printed_content`** | **통장인자내용** — 실무상 여기에 서비스명이 찍힌다 |
| `tran_amt` | 거래 금액 |

페이지당 최대 25건. **가맹점명 필드가 아니라 통장인자내용**이므로 정규화 난이도가 더 높다.

### 2.3 완전 자동 유지

| 데이터 | 출처 |
|---|---|
| 서비스 식별 | 가맹점명 정규화 사전 |
| 금액 | 결제 내역 실측값 |
| 주기·다음 결제일 | 결제 간격 계산 |
| 요금제 변경·가격 인상 | 전월 대비 금액 변동 감지 |

**사용자에게 아무것도 요구하지 않는다.** 최초 인증 1회가 전부다.

## 3. 수익 모델 — 연 1,200원이 성립하는 이유

### 3.1 조회 정책 — 비용의 전부가 여기서 결정된다

**구독은 매달 바뀌지 않는다.** 사람이 구독을 새로 들거나 해지하는 것은 연 몇 번이다.
그런데 초안은 매달 전수 스캔을 가정해 비용을 3배로 부풀렸다. 정책을 다시 정한다.

**갱신 없이도 계속 동작하는 기능이 핵심 기능이다:**

| 기능 | 갱신 필요 |
|---|---|
| 월 구독 지출 합계 | ❌ 식별된 구독 × 금액으로 계산 |
| 다음 결제일 D-Day | ❌ 결제 간격 예측으로 계산 |
| 가격 인상 감지 | ✅ |
| 신규 구독 감지 | ✅ |
| 해지 반영 | ✅ |

**채택 정책 — 2단계 스캔 + 선택적 갱신:**

구독은 1~2장에 몰린다. 보유 카드가 9장이어도 구독이 걸린 카드는 보통 2장이다.
**구독이 없는 카드를 매번 긁는 것이 비용의 대부분**이므로, 먼저 얕게 걸러내고 그 카드만 깊게 본다.

```
1단계  전 카드 × 최근 1개월 스캔          = 3회/카드
       → 가격 지문으로 "정기결제 후보가 있는 카드"를 가려낸다
       → 넷플릭스 13,500원이 1건만 보여도 구독 후보로 판정 가능

2단계  후보 카드만 과거 2개월 추가 스캔     = 6회/후보카드
       → 결제 간격을 확정해 주기를 판정한다

갱신   후보 카드만, 앱 실행 시 월 1회 상한  = 최대 12회/후보카드/년

재스캔 전 카드 × 1개월, 연 1회             = 3회/카드/년
       → 감시하지 않던 카드에 새 구독이 생긴 경우를 늦게라도 잡는다
```

**보유 카드 수에 선형으로 늘어나는 비용은 1단계와 재스캔뿐이고, 둘 다 카드당 연 6회다.**

| 보유 카드 | 1년차 | 2년차 이후 |
|---|---|---|
| 3장 | 708원 | 828원 |
| 5장 | 648원 | 768원 |
| **9장** | **528원** | **648원** |
| 15장 | 348원 | 468원 |
| 20장 | 198원 | 318원 |

**1년차 손익분기가 보유 카드 27장이다.** 카드 수는 더 이상 제약이 아니다.

> ⚠️ **1단계의 한계 — 연 구독을 놓친다.**
> 1개월치만 보므로 연 1회 결제되는 구독(Microsoft 365 등)은 12분의 11 확률로 그 달에 안 보인다.
> 그 카드가 후보에서 빠지면 해당 구독을 못 찾는다.
>
> 보완: ① 연 1회 전체 재스캔에서 점진 발견 ② `카드청구기본정보조회`는 `from_month`~`to_month`
> 범위를 받으므로 **1회 호출로 과거 12개월 청구 총액 추이**를 받을 수 있다. 특정 월에 총액이
> 크게 튀는 카드를 찾아 그 달만 정밀 스캔하면 연 구독을 싸게 잡을 수 있다 — Phase 2 개선 과제.

### 3.2 사용자당 연 손익

§3.1 2단계 스캔 정책, 구독이 걸린 카드 2장, 월 거래 40건, 조회 건당 10원 기준.

| 항목 | 보유 3장 | 보유 9장 |
|---|---|---|

### 3.3 손익분기

| 1인 + 생활비 월 250만 | 3,243만 | 39,167명 |
| 1인 + 연 1억 | 1억 | 120,773명 |

보유 9장 사용자(마진 648원)만 모인 최악의 경우라도 1인 무급 BEP는 **3,750명**이다.

### 3.4 요율 민감도 (§1.5 C1 미확인 대응)

카드 1장·분기 갱신(연 12회) 기준. 건당 요율이 얼마로 나오든 마진이 어떻게 움직이는지.

| 건당 | 연 조회비 | 마진 | 수익률 |
|---|---|---|---|
| 3원 | 36원 | 1,122원 | 94% |
| 7원 (경감 추정) | 84원 | 1,074원 | 90% |
| **10원 (가정)** | 120원 | **1,038원** | 87% |
| 20원 | 240원 | 918원 | 77% |
| 30원 | 360원 | 798원 | 67% |

**손익분기 요율: 카드 1장 기준 건당 96.5원.** 공개된 가장 비싼 조회 API가 15원(계좌실명)이므로
요율 리스크는 사실상 없다. **남은 위험은 요율이 아니라 §1.5의 C3(최소 이용료)와 C4(과금 단위)다.**

### 3.5 비용을 통제하는 규칙

연 1,200원 모델은 **사용자당 변동비가 1,158원(수익 − PG)을 넘는 순간 죽는다.** 따라서:

| 규칙 | 이유 |
|---|---|
| **수동 새로고침 버튼을 두지 않는다** | 조회 1건이 과금된다. 사용자가 당길 수 있으면 비용이 통제 불가 |
| **갱신은 앱 실행 시 월 1회 상한** (§3.1) | 휴면 사용자 비용 0. 참여에 비례하는 구조 |
| **카드 등록 수 상한 없음** | 2단계 스캔(§3.1)에서 1년차 손익분기가 보유 27장. 구독 없는 카드는 갱신 대상에서 빠진다 |
| **CS 티켓을 만들지 않는 설계** | CS 1건(3,125원) = **3년치 수익**. 티켓 1건이 고객 3명의 수익을 날린다 |
| 푸시·알림은 자체 발송(FCM) | 알림톡 건당 과금 회피 |

> **요율은 이 모델의 치명 변수가 아니다** (손익분기 건당 96.5원, §3.4).
> 치명 변수는 두 개다 — **CS 티켓률**(§6)과 **최소 이용료 유무**(§1.5 C3).

## 4. 기능 범위 (MVP)

| # | 기능 | 산출 |
|---|---|---|
| 1 | **구독 인벤토리** | 자동 식별된 구독 목록 + 월/연 합계 |
| 2 | **다음 결제일 D-Day** | 결제 간격 계산 기반 |
| 3 | **가격 인상 감지** | 전월 대비 금액 변동 알림 |
| 4 | **신규 구독 감지** | 처음 등장한 정기결제 알림 ("이거 가입하셨나요?") |
| 5 | **해지 링크** | 서비스별 해지 페이지 딥링크 (사전 DB) |

**4번이 차별 지점이다.** 토스·뱅크샐러드는 고정지출을 보여주지만, **"새로 생긴 정기결제"를 알림으로 쏘지는 않는다.** 무료 체험이 유료로 전환되는 순간이 구독 낭비의 최대 발생 지점이고, 그걸 잡는 것이 이 앱의 존재 이유다.

**MVP에서 빼는 것:** 해지 대행(사람 손 필요), 자산 관리 전반(토스 영역), 예산 관리.

## 5. 경쟁

| | 토스 | 뱅크샐러드 | **v5** |
|---|---|---|---|
| 데이터 | **마이데이터** (정밀) | 마이데이터 | 오픈뱅킹 (제한적) |
| 구독 기능 | 정기결제 자동 추출 | 고정지출 리포트 + 해지 바로가기 | 구독 전용 |
| 가격 | 무료 | 무료 | **연 1,200원** |
| 수익원 | 금융상품 중개 | 보험·건강 중개 | 구독료 |

**데이터로는 이길 수 없다.** 토스는 마이데이터로 "누락이 거의 없이" 정기결제를 추출한다. v5는 오픈뱅킹이라 커버리지가 좁다.

**싸울 수 있는 축 2개:**
1. **신규 구독 전환 알림**(§4-4) — 양사가 하지 않는 기능
2. **구독 전용 UX** — 양사는 자산관리 앱이고 구독은 탭 하나다

> **솔직한 평가:** 무료 경쟁자 2곳이 더 좋은 데이터로 인접 기능을 제공하는 시장에서 연 1,200원을 받는 것이다. **연 1,200원이라는 가격 자체가 거의 유일한 방어**다 — 월 100원은 토스를 쓰는 사람도 추가로 쓸 수 있는 금액이다. 대체가 아니라 **병행**을 노린다.

## 6. CS — 이 모델의 유일한 치명 비용

**CS 1건 = 3,125원 = 고객 3명의 연 수익.** 티켓률 1%만 넘어도 구조가 깨진다.

| 예상 문의 | 자동 처리 설계 |
|---|---|
| 연동이 끊겼다 (토큰 만료) | 자동 재인증 유도 푸시. 문의 전에 해결 |
| 구독이 안 잡힌다 (미분류 가맹점) | **앱 내 "이 결제가 구독인가요?" 1탭 확인** → 사전 DB에 반영. 티켓화하지 않음 |
| 결제·환불 | 인앱결제 또는 PG 셀프 환불 플로우 |
| 카드사 미지원 | 연동 전 지원 카드사 목록 노출 |

**티켓률 목표 0.5% 이하.** 이것을 못 지키면 연 1,200원은 성립하지 않으며, 그때는 가격을 올리는 것이 유일한 선택이다(월 1,900원이면 CS 1건이 0.14년치로 떨어진다).

## 8. 로드맵

| Phase | 범위 | 차단 조건 |

| **0** (1주) | **§1.2 명세 확인.** 개발자 계정 → `카드청구상세정보조회` 응답 필드 확인 | 비용 0. **여기서 경로 B면 사업 재검토** |
| **1** (M0–M2) | 금융결제원 이용계약·보안심사 착수. 가맹점명 정규화 사전 초기 구축 | Phase 0 경로 A 확정 |
